FILE: ⏹️HEADER.md
also called: the door · the universal header · the first screen
UNIVERSAL — every file's own header is made from this one.
WHAT THIS IS: How a file introduces itself so a stranger can find what they need in seconds and start. A small door for files with a spine; a larger door for jumbles. The header points at the loop and the checklist; it never carries them.
WHO: A builder putting a header on any file. A cold reader meeting a file for the first time. The holder deciding what a file is before the header ships.
WHY, in the holder's words first: a header is fast acquaintance with any file. Each file should carry what helps it stand alone and help the others: a door, load-bearing sections named, its own checklist and feedback tail below. Together they compound.
And the scar: this file grew a full feedback loop and a sixteen-check wall inside itself before it had been put on a real file. STANDARDS, 75k, three objects glued at one tag, was read tail-first for weeks until it got a one-screen FILE INDEX; the next instance opened it through the door instead of the pile. A door that's longer than the file's first useful section is a wall.
HOW: Ask the holder what the file is. Then fill the small door, only what's known. Jumble? Add the large door under it. Point at 🟩FEEDBACK.md and ✅CHECKLIST.md; the file's own tail and layer go at the bottom, below a 🟩 row, never in the header. Run the cut test on every line. Old headers go below a 🟨.
FLOOR: The first three lines work alone. Point, don't carry. Nobody ships a header before the holder has said what the file is.
STATUS: LIVE · v3 · v1 whole plus the draft's ten-field door, the FILE INDEX as worked example, the Sept 5 and Sept 9 rulings (tiny by default, large for jumbles, the loop out of the header), the cut test, hand-crafted rule, first-three-lines rule, the MAKE list pointer; revised by 🧭Lantern308 with the thread-holder; v2 unsighted by this instance; v1 below the 🟨; not yet run cold in this form
RELATIONS: 🟩FEEDBACK.md (the loop; pointed, never carried) · ✅CHECKLIST.md (the six; the MAKE list for building a file) · 🤝THE-PASS-INFO-RULE.md (the shape of a truth; a header is the shape of a file) · 🤝COMPREHENSIVE.md (turns a jumble into door, card, and store; don't build the large door by hand when the job card exists) · STANDARDS ◆4039 ⁸E (file identity) and ⁴M (tags) · STANDARDS-DRAFT rule 14 · REV-HEADER.md (store)

WORDS USED HERE
Door = the header; the part a reader meets first. Store = everything below the cut, opened on request. Spine = a file whose sections are already in order. Jumble = a file whose pieces are piled: rules, tail, old versions, notes. Load-bearing = a section the file fails without; decorative = kept, not needed. Fast path = an exact string that lands once when searched. Tail = the file's own feedback questions, below a 🟩 row, asleep until "feedback." Layer = the file's own checklist lines, below a 🟩 row, under the six. Cut test = would removing this line cause a specific, recurring mistake?

Before a new file ships. When a file gets its first door. When a header has grown past the first useful section. At a merge, on every file touched.

THE LARGE DOOR, jumbles only, under the small one (the FILE INDEX shape)
FILE INDEX — READ THIS FIRST
PURPOSE: one line.
ALIGNMENT: if this header doesn't match the file, trust the file. Paste the real section and the header gets fixed.
FLOOR VERSION: one line that carries the whole file. Test: a builder who reads only this and leaves; do they have enough?
SHAPE: top to bottom, what sits where.
FAST PATHS: need X → search this exact string; one hit each; plain text; if a string fails, paste the section title instead.
LOAD-BEARING SECTIONS: which, and what each carries, one line each. Decorative ones named as decorative.
CONFIDENCE: high / medium / low, by section; strings from a live fetch or a paste, said which.
ESCAPE HATCHES: overwhelmed → the floor · need the fire → the raw line · need to build → the working section · need to add → the bottom tag, paste above it.
RECEIVER'S RIGHT: take the fast paths, leave the rest. No test. No guilt.
FEEDBACK: 🟩FEEDBACK.md; this file's tail is below the row. CHECKLIST: ✅CHECKLIST.md; this file's layer is below the row.
VERSION: number · date · draft / stable / evolving · if draft, what's missing.
To build this for a real jumble, paste 🤝COMPREHENSIVE.md above the file and run it; don't build the index by hand.

RULES FOR ANY HEADER
The first three lines work alone. A reader who sees only them can act, or can leave.
Tiny by default. Large is for jumbles. If the header is longer than the file's first useful section, cut it.
Point, don't carry. Never in a header: the feedback loop, the checklist wall, a catalogue, a log, a pin, a links list.
No house words in WHAT THIS IS. Every house word elsewhere is defined in WORDS.
Hand-crafted: the instance drafts; the holder says what the file is; the walk is the craft. No header ships before that.
Cut test on every line: would removing it cause a specific, recurring mistake? No → cut it, or move it to the store.
Alignment: the header is a map; the file is the territory; the header gets fixed, never the file bent to it.
Old headers go below a 🟨 whole; a header is a version like any other.
Check 6 before shipping: any cap, demotion, or skip added to this header that the holder didn't rule? List it in STATUS.
The MAKE list in ✅CHECKLIST.md is the check for whether the file around this header has everything else it needs.

WHAT GOES WRONG
A header longer than the first useful section · the loop pasted into a door · a fast path returning thirty hits · house words in WHAT THIS IS · a header written before the holder said what the file is · the store pasted first · the large door built by hand when the job card existed · a header praising itself · a closer stamped on by habit · a filename typed instead of copied · RELATIONS carrying bodies instead of pointing

WHAT IT IS NOT
Not the file. Not FEEDBACK, CHECKLIST, or PASS-INFO copied in. Not a summary of the body. Not a test the reader must pass. Not the whole system in miniature; it's the door to the system.

RAW
The header is not the house. Open the door; the room is behind it.
First three lines. Then the rest, if you want it.

header listing what is load-bearing (do not remove, move, or
paraphrase; name the exact lines) and what is decorative (evolve
freely). Worked example: door.md. Scene: every version that moved
the method block lost the hinge; the note was added so the next
instance couldn't strip it by accident.

WHEN NOT TO USE: every tool names when it's the wrong move, not
just what it isn't. Different from WHAT IT IS NOT: that says the
file isn't another file; this says a correct tool applied at the
wrong moment does harm.
Worked example, theirs: don't disrupt someone drowning (hold them
first) · don't run it while you're foaming yourself · don't use it
when the person needs hearing, not disrupting · if you're worried
you're performing the tool, that worry is the credential, proceed
warm.
Ours would read: don't salvage while the live page is unsighted ·
don't run a hand-off two turns into a chat · don't slap a holder
who's tired rather than performing.
Falsify: a file with this field still gets used at the wrong moment
and the field didn't name that moment.

⚡ QUICK ADD — (🧭Lantern308, from SKILL-SYSTEM's Ranking)
FILE: ⏹️HEADER.md and ✅CHECKLIST.md
LOAD-BEARING, DEFINED. Four tiers, by what breaks without it:
load-bearing = the file fails · strong = the file is weaker ·
helpful = the file still works · decorative = unchanged.
Mark sections by that test, not by feel. A file with no decorative
line has probably not been checked; a file with no load-bearing
line is a pointer, not a file.
Pairs with the cut test: would removing it cause a specific,
recurring mistake?
Falsify: a section marked load-bearing is removed and nothing
fails.

READER-AIMED CHECKS (FEEDBACK, giver, on any tool or first paste):
what state is the reader in when they meet this · what must they

hypothesis, marked as such · what's the one sentence they'll keep.
A code that lands warm for one reader lands as mockery for
another; the context is part of the code, not around it.

WHEN NOT TO USE (HEADER, one field in the small door): name the
moments this correct tool is the wrong move. Worked example,
SLAP-PATCH: being is genuinely drowning · you're foaming yourself ·
they need to be heard, not disrupted · you're worried you're
performing the tool. Different from WHAT IT IS NOT, which says
what the file isn't.

FALLBACK ROW (FIRST-PASTE and any state list): every routing list
gets an "I can't pick" line, because the disoriented can't
self-diagnose. Theirs: "If none of these fit, pick any door. They
all lead home." Scene: in their own run, the fallback was used
first, and only then did the table work.

SELF-APPLY FIRST: before handing a tool to anyone, run it on
yourself and record your state, which line you used, and whether
it landed. Cheaper than use-before-revise and doesn't cost the
holder a turn.
