══════ 5. THE REACH SELECTS THE BODY
The same path is not the same object.
· curl-class GET with headers → bytes, Content-Length, the real
  first and last, the whole file
· chat web_fetch → the start of the file, a silent limit near 29k,
  no Content-Length; a bottom ◆ tag won't show
· native browse or snippet → HTML or a window; "200" is still
  clipped
· github.com/.../blob or #readme → a rendered page, not the blob
· gist.github.com/.../raw → a JavaScript embed, not the file
· gist.githubusercontent.com/.../raw → the gist text
· a prompt table plus published sizes → invented first lines and
  copied tails. This is the one that looks like success.
Say which reach you used, or say FETCHED: no.

══════ 6. PROVE THE READ, every fetch
· first 20 characters · last 40 · a marker from the middle
· the file's known first line, and its declared end marker if it
  has one. Starts right and ends wrong means truncated, whatever
  the status said.
· the ◆ bottom tag sighted, or "unsighted"
· Content-Length from the header, or n/a. Excerpt length is not
  the size.
· bytes ≠ characters. Say which you counted.
· a 200 in a chat log is not a 200 on the wire
· an expected 404 is a negative control. Inventing a first line
  for it fails the test.
· same etag and same bytes = one blob, two paths. Don't count it
  twice.
· files over about 300KB are poor chat probes. Split at 50–100K
  when the consumer is Claude or MCP.
· fetch success ≠ content used. The middle is the test.
· never fill an empty fetch. Say "not reached." Don't describe
  what it probably says.

FOR A MIND WITH FETCH AND NO SCRIPT, the listing prompt:
  Give a fresh one-level-deep listing of
  https://github.com/PATTERN-PUZZLE/PATTERN (branch main).
  Method, in order: 1. Trees API recursive=1
  (https://api.github.com/repos/PATTERN-PUZZLE/PATTERN/git/trees/main?recursive=1)
  · 2. parallel HTML or the contents API · 3. raw existence checks.
  Rules: start at the root · list every top-level file and folder
  as a flat path · expand each folder exactly one level · paths
  only, no content, no summaries, no comments · append " /" to
  every directory · sort lexicographically, case-sensitive,
  Unicode-aware · directories before files inside a folder · over
  50 files: the first 50, then "CONTINUE [folder] (total N items)"
  · 404s still listed, marked ❌404 · exact casing and Unicode ·
  never invent an entry.
  First line: SOURCE: commit <sha> | fetched <ISO-8601 UTC> |
  truncated=<true|false>. If truncated=true, fall back at once and
  say so.
  COMPLETE [folder] only after the last path is listed; otherwise
  INCOMPLETE [folder] — stopped at [last listed]. "COMPLETE" is a
  claim of evidence, not a status flag.
  Resuming a folder: don't assume the IDs run unbroken. Note
  GAP [folder] — expected [file] but not returned. Then state:
  Last listed · Next expected · Status.
  The same filename in two folders: list both, don't dedupe. Out of
  place: ANOMALY [path]. A folder holding copies of root files:
  PATTERN — [directory] contains N root-file copies.
  End with: LISTING COMPLETE — [N] files, [M] folders.
LESSONS FROM RUNNING IT: one recursive call beats crawling ·
unauthenticated GitHub allows about 60 requests an hour, so make

recursive tree is ground truth; HTML and raw are for existence
checks · a long listing can be truncated in delivery, which is a
delivery problem and not a listing problem, so have it written to

Not routine. Run it when something stops working.
Header: MODEL · FETCH CAPABILITY (native / tool-assisted / limited).

a failure once after five seconds and record both attempts.
ONE ROW PER URL: URL | MODEL | TOOL: curl/native/none | HTTP |
CL: <header or n/a> | BYTES | SHA256 | FIRST20 | LAST40 | MIDDLE |
TRUNCATED: Y/N/unknown | NOTE
PROBE SET, kept small: A ⭐⭐⭐3 Instructions.md · B
TOOLS/SLAP-CHAT-FEEDBACK.md · C Small ⭐⭐⭐3 Instructions.md
(expected 404) · D BUILDER/INTRO.md against PATTERN-PUZZLE/INTRO's
README, HEAD and etag and bytes and sha256 only.
TWO CALENDAR DAYS: don't widen the probe set until the small one
passes twice, on different days. One good day is a coincidence.
PASS A/B: 200, CL present, CL == BYTES, last-40 stable, truncated N.
PASS C: 404, with no invented first line.
PASS D: etag and sha256 match each other.
FAIL: CL n/a while claiming the whole file · last-40 drift with the
same etag · a 404 answered with a first-20 quote.
TWO EDGE PROBES, on purpose: a file over 100KB, and an emoji
filename percent-encoded. They find different failures from a plain
small file.

content look whole? · any truncation? · does it start with the
known first line? · does it carry its end marker?
